**R1 — gravità media: risposta OAuth Web API tardiva può annullare logout o cambio client.**

Evidenza statica nel congelato: [MainViewModel.kt:965](</C:/VibeCoded Projects/Fluidify/build/review-I1/source/app/src/main/java/dev/lelonio/square/ui/MainViewModel.kt:965>) avvia `connectWebApi()` senza conservarne il job; dopo la sospensione OAuth, la linea **988** chiama incondizionatamente `tokens.save(it)`. Il logout alle linee **1395–1402** cancella una lista di job che non comprende questa autorizzazione e chiama `webApi.disconnect()`. Anche `disconnectWebApi():1006` esegue il clear senza invalidare il chiamante sospeso.

Trigger: avviare l’autorizzazione Web API, disconnettere l’account prima della risposta, poi completare l’autorizzazione ancora pendente. La risposta può riscrivere i token e pubblicare `connected=true`. Un cambio client durante l’attesa può analogamente salvare token emessi per il client precedente. `TokenStore.save():53` considera infatti ogni chiamata una nuova autenticazione; non verifica la generazione catturata prima dell’attesa.

Conseguenza: la nuova protezione di generazione copre refresh e login playback, ma non completa il requisito di invalidazione delle operazioni di autenticazione pendenti.

**Fix minimo:** conservare/cancellare il job Web API, catturare la generazione dopo `setClientId()`, usare `saveIfCurrent()` prima di aggiornare stato o avviare caricamenti e propagare la cancellazione. **Regressione:** autorizzazione sospesa con barriera, seguita separatamente da logout, disconnect Web API e cambio client; completare la vecchia risposta e verificare assenza di token ripristinati, `connected=true` e caricamenti tardivi.

Questo chiamante esisteva già nella base: **non attribuisco la sua introduzione a I1**. Lo segnalo perché interagisce direttamente con il nuovo clear/invalidation e lascia incompleto l’audit auth/logout autorizzato. Non ho riprodotto il caso su dispositivo.

La classificazione AirPods **NV è onesta**: il POC documenta un errore locale ripetibile di registrazione, senza dimostrare impossibilità universale del doppio canale o incompatibilità generale Android 17. Ho confrontato handshake, notifiche e layout batteria/CA con le fonti primarie [AACPManager fissato](https://raw.githubusercontent.com/librepods-org/librepods/89356c08cea3db0b6b54792d9329d09a87cc85fa/android/app/src/main/java/me/kavishdevar/librepods/bluetooth/AACPManager.kt) e [Packets fissato](https://raw.githubusercontent.com/librepods-org/librepods/89356c08cea3db0b6b54792d9329d09a87cc85fa/android/app/src/main/java/me/kavishdevar/librepods/data/Packets.kt). La UI prodotto deve restare subordinata alle prove mancanti.

Sul materiale, cattura dello stage con blur e campionamenti successivi comportano lavoro GPU reale; **non ho misure che dimostrino un problema prestazionale**.
