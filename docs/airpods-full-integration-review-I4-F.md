## Finding F-S1-01 — metadata-only owner refresh is discarded

**Severity: medium.** Trigger: an existing downloaded owner has the same ordered URI list as a successful fresh read, but different occurrence dates. This includes a v1 legacy owner whose dates were deliberately migrated to unknown, and repeated occurrences of the same URI reordered/re-added with different dates.

Precise locations:

- `source/app/src/main/java/dev/lelonio/square/ui/MainViewModel.kt:2696`: syncDownloads skips the owner when fresh URI sequence equals known.
- Same file `:2992`: followDownload returns on URI equality after a successful context load, before setOwner at `:2995`.
- Same file `:2736`: syncLikedSongs has the same URI-only shortcut.
- `source/app/src/main/java/dev/lelonio/square/data/DownloadStore.kt:194`: legacy global dates become unknown; `:352` reconstructs dates only from owner occurrences; `:392` updates occurrences only when setOwner is actually called.

The store can represent the new dates correctly. The defect is that the integrated refresh paths never pass them to it when membership/order by URI is unchanged. Legacy unknown dates therefore remain unknown after a successful owner refresh, and known occurrence dates can remain stale. Newest/oldest ordering offline can differ from the fresh online page. This violates S1's per-owner/per-occurrence date behavior; preserving unknown for unrefreshed legacy data remains correct.

**Personally executed proof:** `date-refresh-model.json` records two pure Python branch models. The script asserted all three exact guard expressions exist in the frozen ViewModel, then demonstrated (1) null-to-known dates with identical URI list, and (2) two identical URIs whose occurrence dates swap. Both take the skip branch and retain stale dates. This is an executed model of a statically established branch, **not execution of Kotlin, ViewModel, backend or Android**.

**Archived evidence / test gap:** DownloadOwnerMetadataTest meaningfully checks v1 unknowns, per-owner isolation, repeated occurrences, reopen, mutex contention, cancellation and failed atomic publication. Its refresh cases call store.setOwner directly; they bypass the three ViewModel shortcuts. PlaylistTrackOrderingTest correctly tests known dates, ties and unknown-last in both directions, but cannot repair stale inputs. Their passing XML does not falsify this finding.

**Minimal correction:** compare owner occurrence metadata as well as URI membership before skipping, or add a metadata-only owner refresh that preserves download/failure state. Apply to followDownload, downloaded-playlist sync and liked sync. Do not blindly requeue completed audio or reset failures solely to update dates.

**Proportionate regression:** drive the integrated refresh decision with an existing same-URI owner: legacy unknown→fresh known; repeated same URI with changed occurrence dates; unchanged metadata no-op. Assert offline reconstruction and both date orders after persistence/reopen, with completed files, other owners and failure state preserved. No implementation or new corrective round is performed by this review.
